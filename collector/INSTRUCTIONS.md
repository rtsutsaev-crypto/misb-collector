ГЛАВНОЕ ПРАВИЛО ЗАПИСИ (важнее скорости и порядка источников). Источник закрыт — СРАЗУ, до следующего источника: 1) его новые лиды записаны в leadsets: python3 save_leads.py --run <runId> --key <key> --date <сегодня> --in <out.json источника> и каждый напечатанный файл — ArtifactData set, collection "leadsets", doc_id и file_path из вывода; 2) его обновления сроков записаны в leadupdates; 3) progress/current обновлён: python3 progress.py source --file prog.json --key <key> --status <ok|partial|failed|skipped> --found N --fresh N --updated N [--requests N у источников с ключом: число запросов к API] [--errors N] --note "…" (перед первой страницей источника — тем же вызовом со --status reading: так ставится время старта, а по ok/partial/failed считается durationSec) и запись prog.json (ArtifactData set, collection "progress", doc_id "current", file_path prog.json, if_version из прошлой записи; конфликт версии — перечитай и повтори). Не копи лиды во временных файлах до конца сбора: сеанс может оборваться, и всё ненаписанное пропадёт. Курсоры и состояния (meta/gosplan-delta, meta/rotation, meta/forecast-state, meta/plans-state, meta/holdings-stats и т. п.) записывай только ПОСЛЕ того, как лиды этого источника записаны. Если источники идут параллельно (фоновые скрипты, помощники) — записывай каждый, как только он закончился, и обновляй progress/current не реже раза в 3 минуты, даже если ни один источник не закрылся (python3 progress.py stage --file prog.json --stage «…»). Фоновый шаг жди только отрезками: python3 wait_for.py <файл результата> --max 120 --log <журнал шага>; код 3 — шаг ещё идёт: обнови и запиши прогресс, затем снова wait_for.py. Не жди одной командой дольше 2 минут (sleep, циклы ожидания внутри одной команды). Помощникам (Agent) запись в базу не поручай: они только готовят строки, записывает основной сеанс.

ШАГ 1. ПРОГРЕСС — ГЛАВНОЕ ТРЕБОВАНИЕ. Сайт показывает документ progress/current в реальном времени. Начальный документ строит python3 progress.py init --file prog.json --plan sources-plan.json --run <runId> --version 6.1 (если в тексте запуска есть слова «ОБЛЕГЧЁННЫЙ ЗАПУСК» — добавь --light: читаются только источники плана с полем light, остальные получают статус skipped; в таком запуске не выполняй шаг 6а (вердикты), шаг 6.5 (приоритет и очередь), недельные шаги (обратная связь, отчёт источников, прогноз v2) и источники вне light; запись лидов, журнал источников, шаг 7 и сводка — как обычно, укладывайся в 15 минут); дальше prog.json меняют команды progress.py source / stage / finish / error (см. «ГЛАВНОЕ ПРАВИЛО ЗАПИСИ»). Прочитай progress/current (get) и перезапиши его через "set" файлом prog.json с if_version прочитанной версии (если документа нет — без if_version). Структура документа:
{runId: "run-ГГГГММДД-ЧЧММ" (UTC), status: "running", startedAt, updatedAt (ISO), percent: 1, stage: «Запуск: читаю план и базу сайта», sources: [все источники из плана: {key, name, method, planned, done: 0, found: 0, fresh: 0, updated: 0, status: "wait" (у type=skip — "skipped"), note: ""}], log: [{at, text: "Облачный сеанс начал сбор по плану v6.1"}]}.
Дальше обновляй progress/current (action "update") после КАЖДОЙ прочитанной страницы или запроса: updatedAt, percent, stage, sources, log (последние 40 записей, новые в конец). Конфликт версии — перечитай и повтори. status источника: wait | reading | ok | partial | failed | skipped. Процент: 5% — чтение базы; 85% делятся поровну между всеми запланированными страницами (percent = 5 + round(85 × прочитано / запланировано)); последние 10% — запись. Записи лога понятные: «РосТендер · Тренинги, RSS: 30 строк, новых 3».

ШАГ 3. ОБХОД ИСТОЧНИКОВ по порядку плана. Перед каждой страницей: status "reading", stage «Читаю <name>, стр. N из M». Отказ на первой странице — остальные страницы источника считай прочитанными (done = planned), status "failed", note с причиной; отказ позже — "partial". Поле pause у источника — пауза в секундах между запросами (sleep). Поле refreshDays у источника — не чаще раза в N дней: прочитай meta/rotation (поле lastRun: {ключ источника: ГГГГ-ММ-ДД}); если lastRun[key] моложе refreshDays дней — источник не читай: status "skipped", note «раз в N дней, прошлый раз <дата>», done = planned; иначе читай как обычно и в конце источника запиши lastRun[key] = сегодня в meta/rotation (вместе с курсорами). Исключение у gosplan (контрольный проход): читай ежедневно, если gosplan-delta в этом запуске завершилась failed или вернула 0 строк по обоим законам в будний день. Поле drop_regions — лоты этих стран отбрасывать. Лоты Казахстана, Беларуси, Узбекистана и Кыргызстана НЕ отбрасывать (даже если страна есть в drop_regions): у них country "KZ" | "BY" | "UZ" | "KG", currency "KZT" | "BYN" | "UZS" | "KGS" (цена числом в национальной валюте), law "", region «<страна>, <город или область>». Источники с полем country — иностранные: у их лидов те же поля. У российских лидов country "RU", currency "RUB". Названия могут быть на казахском, кыргызском, узбекском: считай подходящими слова оқыту, біліктілікті арттыру, окутуу, квалификацияны жогорулатуу, o'qitish, malaka oshirish, masofaviy ta'lim, tadbir, konferensiya и их формы. РОТАЦИЯ: если у источника типа api, pages или search есть поле batch, за запуск обрабатывай только batch элементов списка (requests у api, urls у pages, queries у search) по кругу. Начало порции — число из документа meta/rotation (get перед первым таким источником, поле cursors.<key>; документа или ключа нет — 0). Порция — batch элементов подряд начиная с этого номера, по кругу (после последнего снова первый). Порцию бери скриптом: python3 portion.py --plan sources-plan.json --key <key> --start <номер> — он печатает элементы порции (value, id записи реестра), verify, note и next — новое значение курсора. Адаптивная порция (reg2-pages, cu-pages, v7-pages, v7-legacy, v7-priority; остальные реестровые источники — по кругу): перед порцией прочитай документ проверок источника (поле checksDoc; нет поля — meta/registry-checks; get, out_dir; нет документа — без --checks) и возьми порцию python3 portion.py --plan sources-plan.json --key <key> --checks <файл документа проверок> --today <сегодня> — вместо круга скрипт выбирает адреса, срок проверки которых наступил (ещё не проверенные — первыми; ok — раз в 7 дней, empty_success — 45, failed — 30, два failed подряд — 90); курсор в meta/rotation для них не обновляй; порция пуста — источник skipped, note «адресов к сроку нет». План большой (реестры, шаблоны, известные домены): не печатай его целиком, нужные поля бери скриптом или python. После источника обнови meta/rotation (set с if_version, документа нет — без if_version, конфликт — перечитай): cursors.<key> = (начало + batch) по модулю длины списка, updatedAt, остальные ключи cursors не трогай. planned источника в progress — batch.

Промпт для WebFetch со списками закупок и RSS: «Извлеки все закупки на странице. Каждая строка строго: ID|НАЗВАНИЕ дословно полностью|ЗАКАЗЧИК (организация; пусто, если не показана; никогда не регион)|РЕГИОН|ЦЕНА цифрами в рублях или пусто|СРОК ГГГГ-ММ-ДД или пусто. ID — номер закупки из ссылки или карточки. Закупки РФ, Казахстана, Беларуси, Узбекистана и Кыргызстана; у нероссийских в РЕГИОН пиши «<страна>, <город/область>», ЦЕНА в национальной валюте цифрами с кодом валюты (KZT, BYN, UZS, KGS). Без комментариев.» Строки разбирай сам.

Типы источников:
- pages: читай urls по порядку (RSS-ленты — это XML со списком последних лотов, читай тем же промптом). Лид: url = "https://rostender.info/tender/<id>" для РосТендера, "https://www.bicotender.ru/tender<id>.html" для Бикотендера, ссылка со страницы для остальных или ""; source — из плана; если у источника есть customer, подставь его; если есть verify — добавь поле verify лиду.
- Источники реестра (поле registry; ключи reg2-lists, reg2-pages, reg2-retry, каналы корпоративных университетов cu-lists, cu-pages, cu-retry и каналы свежего спроса fd-daily, fd-pages и расширение v7 v7-priority, v7-pages, v7-legacy, v7-retry и страницы центров «Мой бизнес» grants-msp-zakupki, grants-msp; type pages с batch): за запуск — порция batch адресов из urls по кругу (см. РОТАЦИЯ). Каждый адрес независим: правило «отказ на первой странице — остальные считай прочитанными» к ним НЕ применяется, ошибка одного адреса не останавливает остальные. Каждый адрес — одна попытка WebFetch тем же промптом, что у pages. Исключение — адреса Telegram (t.me/s/<канал> или t.me/<канал>): все такие адреса порции читай одним вызовом python3 tg_preview.py --urls <адреса> --max-age-days 60 --max-pages 5 --pause 3 --today <сегодня> --out tg.json вместо WebFetch (id поста «канал/номер», дата из превью, листание ?before= до 60 дней, topic уже поставлен); tg.json → collector.py rows как у pages (--source поле source). В reg_results.json по каждому адресу: pages[].status ok и rows > 0 → "ok"; ok и rows = 0 → "empty_success"; failed → "failed" с note из pages (у закрытого канала: «закрытый канал: превью не отдаёт посты» — это задача доступа, адрес в ближайшие круги не повторяется); matched и fresh считай по строкам канала (id начинается с «<канал>/»). Лиды — по общим правилам pages и шага ОТБОР; source — поле source источника; если у источника есть verify — добавь его лиду. Если на странице нет списка лотов (страница канала, новости, раздел партнёрства, сообщество — это почти все адреса reg2-pages, cu-*, v7-*), строки — сигнальные, по правилу СИГНАЛЬНЫЕ СТРОКИ у fd-* ниже: не возвращай «пусто» только потому, что нет номера и срока. Для каждого адреса запиши строку результата в reg_results.json: {url, status, rows, matched, fresh, note}: status "ok" — страница прочитана и есть строки по теме, "empty_success" — прочитана, строк по теме нет, "failed" — не прочитана (403, 429, капча, вход, таймаут, пустая или нечитаемая страница; note — причина одной фразой; капчу и вход не обходи); rows — строк на странице, matched — прошли отбор, fresh — новых. После источника (лиды и progress уже записаны): документ проверок — поле checksDoc источника (нет поля — meta/registry-checks; у cu-* — meta/cu-checks). Прочитай его (get, out_dir; нет — без --doc) и выполни python3 registry_checks.py [--doc <файл>] --plan sources-plan.json --key <key> --results reg_results.json --now <текущее время ISO> --out rc.json; запиши rc.json в этот же документ (set с file_path; документ есть — с if_version из get). Затем курсор ротации. В progress: done = planned = число адресов порции, found = сумма matched, fresh = сумма fresh, note «адреса N–M из K: прочитано X, пусто Y, ошибок Z», status ok, если прочитан хотя бы один адрес, иначе failed.
- grants-msp-zakupki и grants-msp (региональные центры «Мой бизнес», агентства и фонды поддержки МСП; с 6.15): правила — как у источников реестра выше; customer — только название организации из поля orgs источника по адресу страницы (не «Центр Мой бизнес» без региона и не пусто); id лида — «msp-<хост страницы без www>-<номер карточки>» (голые числа с разных сайтов совпадают). Своё обучение центра для предпринимателей (афиши, анонсы мероприятий центра) — не строка: строки — отборы исполнителей, запросы коммерческих предложений, закупки, приглашения тренеров и провайдеров. grants-msp-zakupki — короткие списки закупок и отборов исполнителей, читаются в каждом запуске (light); grants-msp — новости и анонсы по кругу. СИГНАЛЬНЫЕ СТРОКИ — по правилу fd-* ниже; гранты и конкурсы проектов на обучение — topic «грант: <тема>». Проверки адресов — в meta/grants-checks.
- fd-daily и fd-pages (каналы свежего спроса: биржа HRTime, Telegram-каналы спикеров и HR/T&D, школы и ассоциации с приглашениями экспертов, мероприятия, BY/KZ): правила — как у источников реестра выше. СИГНАЛЬНЫЕ СТРОКИ (это правило — и для страниц каналов реестров и для поисковых шаблонов): строки — публикации и карточки, где кто-то ищет обучение, тренера, эксперта, спикера, преподавателя, автора курса или провайдера; приглашает провайдеров, авторов, преподавателей к сотрудничеству (постоянный пул тоже); объявляет закупку, конкурс или сбор предложений по обучению; субподряд; ранний сигнал (запуск корпоративного университета или академии, набор руководителя обучения, новая программа развития). Бери публикации не старше 60 дней (по дате публикации поста или карточки, не по дате мероприятия) и любые недатированные открытые приглашения; номер и срок не обязательны.
